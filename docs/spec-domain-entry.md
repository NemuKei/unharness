# 独自ドメインとAIから開くUnharness

2026-09-09採用。操作画面のURLを独自ドメインにし、まずCodex Desktopのアプリ内ブラウザーで開く。Claude Codeでの確認は後続とする。ローカルの設定・比較・作品の保存場所は利用者のPC内に残す。これは次の実装契約であり、現在のlocalhost専用サーバーの対応実績ではない。[統合計画](superpowers/plans/2026-09-09-mac-product-experience.md)を参照する。

## 利用者の流れ

サイトで試す・導入する → 普段のAIに「アンハーネスを開いて」と頼む → 管理Skillが登録済みのローカル処理を起動または再利用する → アプリ内ブラウザーで独自ドメインの画面を開く → このPCとの接続を許可する → モードを選ぶ。

細かい設定は[AIによる設定相談](spec-guided-setup.md)へ渡す。画像制作は別の[オリジナル作成Skill](personalization.md#optional-creation-skill)へ渡す。管理の入口はNormal・UNSEAL・TRUEFORMのすべてで保持する。画面を開くだけではモードを変更しない。

## 責任とデータ

| 場所 | 受け持つもの |
| --- | --- |
| 独自ドメインの静的サイト | 導入案内、サンプルのデモ、操作UI、公開用の作者表記とリンク |
| 利用者のブラウザー内 | UIの実行、一時的な接続、表示に許可された要約と画像。公開サーバーへの自動送信は行わない |
| PC内のローカル処理 | 登録範囲、設定の読み書き、保存版、比較記録、画像の検証と保存、競合確認、復旧 |
| 同梱の管理SkillとMCP | 起動・接続先の引き渡し、状態確認、明示された操作、AIとの設定相談 |

個人データを公開サーバーへ保存しないことと、公開サイトのJavaScriptが表示データを扱うことは別である。許可された配信元が侵害された場合、そのUIへ渡した情報と操作権限も影響を受ける。接続元チェックだけでは防げないため、遠隔origin向けAPIを必要な要約と操作に限定する。

## プラグインとWebMCPの役割

関連SkillとローカルMCPを一つのUnharnessプラグインとして配布する。管理の入口、設定相談、オリジナル制作をまとめ、ページを閉じても起動・状態確認・復旧を呼べるようにする。TRUEFORMでもプラグインの管理機能と接続を保持し、制作の詳細は依頼時だけ読み込む。

公開ページにはWebMCPを追加する。接続前は公開の導入案内と合成デモだけを扱い、ローカル側で認可した接続後に、状態確認・変更計画・適用・外観選択を提供する。各実装はGUIの同じ操作クライアントとMac内の共通サービスを使う。WebMCPから独自のファイル書換えや設定操作を実装しない。接続の承認、管理対象の追加、任意パス・任意コマンドをWebMCPの権限に加えない。

現在の仕様の`document.modelContext`を機能検出し、登録時の`AbortSignal`で解除とページの寿命を管理する。接続切れ、ページ離脱、登録失敗、同名の再登録、処理途中の切断を検証する。未対応・登録失敗でも通常のGUIとローカルMCPを利用できる。SideBizの既存アダプターの責務分離を参考にし、対応をMac Codexの実際のブラウザーで確認する。[WebMCP仕様](https://webmachinelearning.github.io/webmcp/)は策定中であり、一般のブラウザー全体への対応を前提にしない。

設定本文・認証情報・メモリ本文・生の会話や実行出力を公開UI向けの標準レスポンスに含めない。詳細な私的情報を開く機能は、ローカル画面または明示した別の権限境界で扱う。利用者が自分のAIへ選択して渡す情報は、そのAI側の通常の取扱いに従う。

## 接続の契約

- 接続はloopbackのみで待ち受け、外部ネットワークへ設定操作用ポートを公開しない。
- 信頼する公開画面は、利用者が指定した正確なHTTPS originで管理する。任意のOrigin、ワイルドカード、名前の似たドメインを許可しない。
- アカウント登録は要求しないが、サイトとこのPCの紐付け・短期間の接続認証は行う。公開ページを表示しただけで接続を許可しない。
- 初回の接続許可は、公開UI自身が偽造できないローカル側の経路で確定する。対象アプリ・登録範囲と許可する操作を表示する。
- ローカルの管理経路が発行した短期間・一回限りの引き渡し情報を使い、引換え後の接続は起動ID・登録範囲・originへ結び付ける。再利用・期限切れ・別scope・別originは拒否する。
- 通常の接続トークンをURLや公開ログへ書かない。引き渡し情報をURLのfragmentに載せる場合も、読み取り後に除去し、短期間で失効させる。
- 接続元チェック、Host、CSRF対策、CORS、トークン、入力上限をそれぞれ検証する。CORSを許可しただけで認証済みとしない。
- 管理対象の追加、任意パスの読取、任意コマンド、権限変更を公開UI向けの接続権限に含めない。設定を変える前の計画・独立編集・復旧の検査はPC内の共通処理が行う。
- 同じ依頼でサーバーやタブを増やさない。既存のプロセス・接続先は所有関係と起動IDを確かめて再利用し、別プロセスのポートを勝手に停止しない。
- 画面やAIが切断された後の未確認操作は、操作IDで結果を確認する。新しいIDを作って二重に実行しない。

## 表示と故障時の動作

接続先は「このMac・Codex」等の短い表示にし、未接続・切断・別環境・対応外・不明を区別する。モデルやタスクの状態は、確認できた情報と日時の範囲で表示する。切替後は新規タスクへ案内し、今の会話に読み込み済みの設定まで変わったとは表示しない。

同梱したローカル画面と復旧手順を、サイト・インターネット・AIが利用できない場合にも残す。公開画面で許可を拒否しても、PC内の設定と保存した作品を失わない。復旧は独立編集を確認してから行う。

アプリ内ブラウザーでの接続は各アプリの許可・管理設定を尊重する。対応しない環境は理由と使えるローカル入口を示し、アプリ内で開いたとは報告しない。許可を無効化する設定変更を利用条件にしない。

## 配布・作者の導線

独自ドメインは導入と操作の両方の入口にする。初回導入では対応AI・OSを選び、検証済みのプラグイン / Skill / ローカル実行環境を用意する。専用のMacアプリやWindowsインストーラーを必須にせず、使う場合は費用と配布条件を別に確認する。

導入前のデモは架空の設定だけを使う。画面の最下部に小さな作者名とサイトへのリンクを置く。ブランド名・URLは利用者が指定し、秘密情報や接続情報をリンク・解析・広告へ渡さない。

## 受入れ条件

1. MacのCodex Desktopで、依頼→ローカル起動→独自ドメイン表示→接続→状態取得を実行して確認する。Claude Codeは後続の対応時に同じ確認を行う。
2. 許可、拒否、期限切れ、再起動、古いタブ、二重操作、別scope、別originを確認する。
3. 本物の公開HTTPS originからloopbackへ接続する実機結果を残す。ローカルの二つのポートだけではブラウザーのローカルネットワーク許可を検証したことにしない。
4. GUIとAIの切替で同じ保存版・操作結果を得て、開いた画面にも外部変更を反映する。
5. サイトとAIを利用できない条件で、ローカル復旧を実行し、独立編集を保持する。
6. Windowsは後続に同じ確認を行う。Macや通常のブラウザーの証拠からWindowsのアプリ内対応を推定しない。
7. 公開ページのWebMCPを実際に列挙・呼び出し、画面と同じ保存版・結果になること、未接続時には実設定を操作できないことを確認する。プラグインの導入・更新・TRUEFORMでの管理入口・ページを閉じた復旧も別に検証する。
