# Unharnessの価値とOSSでの伝え方

2026-09-13更新。Unharnessの価値と公開時の伝え方。機能の契約は [spec.md](spec.md)、現在の実装状況は [status.md](status.md) を参照する。

## 価値の中心

作者の公開目的は、面白いものを完成させて無料で使ってもらい、外部から確認できる制作実績を積むこと。2026-09-09にMITでのOSS公開を選択した。公開サイトのデモと導入体験を中心に据え、GitHubで設計・実装・検証の根拠を確認でき、作者サイトへもたどれるようにする。課金や販売の仕組みは今回の目的に含めない。

**ハーネスを気軽に着脱して比較し、今のモデル・環境・仕事に合う構成を自分で見極められること。**

Skillや常設の指示を積み上げると、どれが今の仕事に役立っているか分からなくなることがある。外した状態も試したいが、設定を探し、退避し、別条件を作り、元へ戻す準備が必要だと、小さな疑問を試すまでが遠い。

そこで、今の構成を残したまま、思い立ったときに装備を外したり戻したりして試せるようにする。比較した結果、今のままがよいと分かることにも価値がある。利用者が選ぶのは、手元の仕事で得た結果に合う構成。ゼロモードは比較の出発点の一つになる。

特に確かめたいのは、過去のモデルを補うために追加したAGENTS.md／CLAUDE.mdやSkillの手順が、今も必要かどうか。メモリと標準の作業継続機能を使ったまま、自作・自分で追加した指示とSkillを中心に比較する。hookは任意の補助処理に絞り、必須要件や権限は保持する。普段はモードを選ぶだけにし、細かい設定は近くの「設定をAIに相談」から普段のAIと見直す。[対象範囲と見直し案](harness-scope.md)を参照する。

## 導入と日常の入口

独自ドメインのサイトから、導入前のデモとAIへの導入案内へ進める。初回Mac版では、導入後にCodex Desktopへ「アンハーネスを開いて」と頼み、同梱の管理Skillを通してローカル接続を確認する。公開操作画面は同じドメインとローカルの許可を使う。Claude Codeの実機対応は後続とする。設定・比較記録・作品はPC内に保存し、サイトやAIが使えない場合のローカル復旧も残す。

零式でもUnharnessの管理Skillと操作・復旧の接続は保持する。モード、モデル、登録対象、次の新規タスクへの反映を分かるようにし、モデルが変わったときや新しいSkillを作ったときには、既存の版を残してAIと設定を見直す。

外観はいつでも任意に作れる。本体・拘束具・背景をテンプレートで分け、自分のAIと希望や参考画像を相談し、作ったパーツをローカルから読み込む。標準パーツとの組合せや作り直しもでき、性能が悪化しても好きな見た目を使える。性能は別の数値・説明で示す。最下部には小さな作者名とサイトへのリンクを置く。

これらは初回Mac Codex版に実装し、[実機の導入・公開操作・復旧](evidence/2026-09-13-mac-codex-completion.md)と[外観の保存・再利用](evidence/2026-09-13-awakening-motion.md)を確認した。[統合計画](superpowers/plans/2026-09-09-mac-product-experience.md)は採用時の実装順と判断の履歴として残す。作品パックの共有や公開ギャラリーは、ローカルでの作成・保存・再利用ができた後に検討する。

## 一文で伝える

公開ページの冒頭では、モデルが変わったときの具体的な疑問から入る：

> **モデルは変わった。装備は、そのまま？**
> 書き直す前に、一度外して使ってみる。

説明文：

> いつもの構成を保存して、選んだ追加指示を外したり、自作・外部Skillの自動使用を抑えたり。ふだんの仕事で試して、必要なら戻せます。

英語の草案：

> **New model. Same old harness?**
> Before rewriting it, try taking it off.

> Save your usual setup, then try your everyday work with selected instructions removed or optional Skills called only when you choose. Restore what you need and keep the setups that fit.

公開ページは「新モデルへの問い → 画面とチャットから使える4機能 → 設定例と連動した変身プレビュー → 自分だけの外観 → 導入と対応予定」の順で伝える。初期設定・設定変更・モード切替・外観は同じ機能で、画面から操作する入口と、導入したAIのチャットで依頼する入口を持つ。初回登録・接続許可など必要な確認だけ、このMacの確認画面へ案内する。デモを主な入口、導入を次点にし、導入済みの接続は控えめに置く。デモは設定例と外観の体験で、AIの回答や性能を測定しない。

普段の操作画面は「モード・設定・外観」を中心にする。未登録が確認できた初回は設定へ案内し、モード選択・変更内容・確定と、押せない理由・解消する入口を同じ領域へ置く。公開とローカルで操作名をそろえ、比較履歴や接続・復旧は必要時に開く。[操作画面の契約](spec-workbench-ux.md)を参照する。

「比べる」より先に、自分の普段の依頼で使って確かめる行動を説明する。モデル更新は強い入口として使い、仕事に合わないと感じたときにも試せることを添える。遊び心は、設定例と姿が一緒に変わる体験で伝える。外観を選んでも設定や性能評価は変わらない。

## 最初に届ける利用者と場面

最初に届けるのは、MacのCodexデスクトップへ自分のSkillや指示を追加しており、構成の違いを実際の仕事で試したい人。初回のMac Codex製品は合意した範囲で完成している。2026-09-13に、次はWindows版Codex、その後にClaude Codeへ取り組む順序を採用した。最終的にはmacOS・Windowsで両アプリへの対応を目指す。

- モデルを変えたので、いつもの装備が引き続き合うか確かめたい。
- AIの進め方が仕事に合わず、どの追加指示が影響しているか試したい。
- 気になるSkillを追加し、ある場合とない場合の違いを見たい。
- 開発とレビューなど、用途ごとに気に入った構成を残しておきたい。

モデル更新は利用するきっかけの一つ。日々の小さな疑問から比較を試せることを主な体験にする。需要の広さや継続利用の頻度は未検証。

入口はモードを1つ選んで普段の依頼を試すこと。記録した結果を後から振り返り、詳しく確かめたいときだけ同じ開始条件で別モードへ再実行する。3モードへの同時投入は初期体験に含めない。異なる仕事の使用量をそのまま比べて性能差と断定しない。

## ウリと、それを支える体験

| ウリ | 利用者の体験 | 公開時に示す裏付け |
| --- | --- | --- |
| 思い立ったら、外して試せる | 「限定解除に切り替えて」と頼むか、画面でモードを選ぶ | 設定保存から別構成での新規タスク開始までの実演 |
| 自分の仕事で違いが分かる | 同じ依頼を同じ開始状態から試し、成果物と評価メモを並べる | 比較条件、実行例、揃えられない条件の明示 |
| 戻し方が分かるから試しやすい | 今の構成を保存し、切替後も以前の装備へ復帰できる | 検証済みの復帰範囲、失敗時の回復、外部変更との衝突処理 |
| よかった組み合わせを残せる | 「今の設定をお気に入りに登録して」で保存し、後から呼び戻す | 登録時の版を再現するセーブ／ロードの実演 |
| 画面からもAIへの依頼からも使える | 普段のCodexで依頼し、Web画面でも状態を確認する | 二つの入口で同じ処理結果になることの確認 |
| 試すこと自体を楽しめる | 装備が外れ、中からAI本体が現れる演出。演出オフでも同じ操作ができる | 選択した画風、演出のオン／オフ、状態表示の実演 |

最初に押し出すのは「気軽に試せる」「比較して判断できる」「よかった構成を残せる」の三つ。復帰・状態の確認は、その気軽さを支える製品の基礎。ゲーム風の演出は、触ってみたくなる入口と状態理解に使う。

## READMEで見せる最初の一周

1. 今の構成をお気に入りに登録する。
2. 通常・限定解除・零式から別の構成を選ぶ。
3. 選んだモードで新しいタスクを始め、依頼と開始状態を記録する。
4. 成果物、手戻り、所要時間、取得できる使用量と評価メモを振り返る。必要なら後で同じ開始条件から別モードでも試す。
5. 必要な要素を戻す、または手動のみへ変える。
6. 気に入った組み合わせをお気に入りとして残す。以前の構成も呼び戻せる。

画像・デモの主役もこの一周にする。起動画面や解除演出だけでは、比較してお気に入りを残す価値が伝わらないため、公開用のデモは最後のセーブまで含める。

## 説明と検証の約束

- 「合う」は、モデル・環境・依頼・評価の観点に結び付けて説明する。全員に共通の最強構成を前提にしない。
- 外してよくなることも、変わらないことも、悪くなることも比較結果として残す。通常装備を再採用できる体験にする。
- 比較を用意する手間を下げることと、比較結果の因果関係を証明することは区別する。単発の結果から一般的な性能向上を主張しない。
- 同じモデル・推論設定・依頼・開始ファイル・道具・権限を可能な範囲で揃える。メモリや外部サービスなど、共有・変動する条件を記録する。
- 「次回用の設定」と「現在のタスクで確認できた状態」を区別する。新しいタスクでの反映が必要なら明示する。
- ゼロの対象は、選択した管理可能な追加手順・Skill等。仕事の条件と実行権限は保持し、切替用の最小接続口など残る要素も記載する。
- 本体が解き放たれる演出は、ハーネスの着脱を表す。性能の保証や実行権限の解除として宣伝しない。

これらは長い注意書きとして冒頭を埋めるのではなく、各機能の説明と比較・互換性ドキュメントへ配置する。

## 初期版の範囲を守る判断軸

残す核は、保存、3モード、設定・適用状態の表示、条件を揃えた比較、お気に入り、復帰、WebとAIの二つの入口、オフにできる演出。

範囲を絞る際は、対応OS・ツール・バージョンと演出の種類を絞る。構成の世界ランキング、共有マーケット、クラウド同期、自動の最適構成選定は初期の核に含めない。

仮説を観測する最小の場面は、利用者が実際の依頼で別構成を試し、結果を見て採用・維持・復帰のいずれかを選び、その理由と構成を残せること。性能差がなかった場合も、この判断まで辿り着けたかを見る。

利用を広げるための追加案は [feature-candidates.md](feature-candidates.md) に分けた。採用前の仮説であり、既存の初期仕様や実装順を自動的に増やすものではない。

## OSSのDocsを育てる方針

READMEは現在使える価値と対応範囲を明示し、将来案と過去の検証はリンク先で区別する。[英語README](../README.md) と [日本語README](../README.ja.md) を用意し、機能と対応範囲の変更を両方へ反映する。

現在は登録した任意ソースの保存・準備・復帰、ローカル／公開GUI、日常の比較記録、任意の順次再実行、MCP、自由な外観制作・保存・再利用を実装し、初回Mac Codex版の合意範囲を検証した。個別プラグインOFFや他のOS・アプリ、実行状態全体の観測、普遍的な性能改善を含むものではない。最新の範囲は [status.md](status.md) に記録する。インストールコマンド、対応保証、取得できる指標は、実装と検証ができたものだけを公開手順に記載する。

公開前には、英日両方の文書の各機能説明、画面、手順、対応表を実装と証拠に照らして確認する。未実装の文章はロードマップへ移すなど、第三者が現在の機能と誤認しない状態にする。

## 確定した名前と開発順

製品名は **Unharness**。モードの演出上の呼び名は **限定解除 — UNSEAL** と **零式 — TRUEFORM**。

対象OSはmacOSとWindows、対象アプリはCodexデスクトップとClaude Codeデスクトップ。2026-09-13の開発順は **Mac版Codex → Windows版Codex → Claude Code対応 → 統合確認**。Claude Codeは自分の連携実装・検証を担当し、Codexが全体の整合性を確認する。対応予定と、実機で確認した利用可能範囲を分けて案内する。

この順序は [delivery.md](delivery.md) に受け渡す成果と受け入れ条件を含めて記載した。専用repoの初期化は完了時点での出発点であり、各組み合わせの対応完了は実機検証に基づいて判断する。
