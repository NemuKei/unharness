# Unharnessの価値とOSSでの伝え方

2026-09-08更新。Unharnessの価値と公開時の伝え方。機能の契約は [spec.md](spec.md)、現在の実装状況は [status.md](status.md) を参照する。

## 価値の中心

**ハーネスを気軽に着脱して比較し、今のモデル・環境・仕事に合う構成を自分で見極められること。**

Skillや常設の指示を積み上げると、どれが今の仕事に役立っているか分からなくなることがある。外した状態も試したいが、設定を探し、退避し、別条件を作り、元へ戻す準備が必要だと、小さな疑問を試すまでが遠い。

そこで、今の構成を残したまま、思い立ったときに装備を外したり戻したりして試せるようにする。比較した結果、今のままがよいと分かることにも価値がある。利用者が選ぶのは、手元の仕事で得た結果に合う構成。ゼロモードは比較の出発点の一つになる。

特に確かめたいのは、過去のモデルを補うために追加したAGENTS.md／CLAUDE.mdやSkillの手順が、今も必要かどうか。メモリと標準の作業継続機能を使ったまま、自作・自分で追加した指示とSkillを中心に比較する。hookは任意の補助処理に絞り、必須要件や権限は保持する。普段はモードを選ぶだけにし、必要なときだけ下の「対象を調整」を開く。[対象範囲と見直し案](harness-scope.md)を参照する。

## 一文で伝える

推奨する短いコピー：

> **ハーネスを、気軽に試着する。**
> 外して、比べて、気に入ったら残す。

説明文：

> Skillや追加指示を気軽に着脱し、同じ仕事で違いを確かめる。今のモデルと環境に合う組み合わせを見つけたら、お気に入りに保存してまた使える、ローカルのハーネス比較ツール。

英語の草案：

> **Try on your AI harness.**
> Take it off. Compare. Keep what fits.

> Try different combinations of skills and instructions on your own work. Find what fits your current model and environment, and save the setups you want to use again.

「見直し」「整理」「最適化」は利用の結果として説明できる。導入部は、利用者が軽い気持ちで試せることと、その比較が判断に役立つことから始める。

## 最初に届ける利用者と場面

最初に届けるのは、MacのCodexデスクトップへ自分のSkillや指示を追加しており、構成の違いを実際の仕事で試したい人。MacのCodex版の核を仕上げ、MacのClaude Code対応と製品の仕上げを進める。Windowsも設計対象として保ち、Mac版の完成後にCodex、Claude Codeの順で対応する。

- モデルを変えたので、いつもの装備が引き続き合うか確かめたい。
- AIの進め方が仕事に合わず、どの追加指示が影響しているか試したい。
- 気になるSkillを追加し、ある場合とない場合の違いを見たい。
- 開発とレビューなど、用途ごとに気に入った構成を残しておきたい。

モデル更新は利用するきっかけの一つ。日々の小さな疑問から比較を試せることを主な体験にする。需要の広さや継続利用の頻度は未検証。

入口はモードを1つ選んで普段の依頼を試すこと。記録した結果を後から振り返り、詳しく確かめたいときだけ同じ開始条件で別モードへ再実行する。3モードへの同時投入は初期体験に含めない。異なる仕事の使用量をそのまま比べて性能差と断定しない。

## ウリと、それを支える体験

| ウリ | 利用者の体験 | 公開時に示す裏付け |
| --- | --- | --- |
| 思い立ったら、外して試せる | 「限定解除に切り替えて」と頼むか、画面でモードを選ぶ | 設定保存から別構成での新規タスク開始までの実演 |
| 自分の仕事で違いが分かる | 同じ依頼を同じ開始状態から試し、成果物と評価メモを並べる | 比較条件、実行例、揃えられない条件の明示 |
| 戻し方が分かるから試しやすい | 今の構成を保存し、切替後も以前の装備へ復帰できる | 検証済みの復帰範囲、失敗時の回復、外部変更との衝突処理 |
| よかった組み合わせを残せる | 「今の設定をお気に入りに登録して」で保存し、後から呼び戻す | 登録時の版を再現するセーブ／ロードの実演 |
| 画面からもAIへの依頼からも使える | 普段のCodexで依頼し、Web画面でも状態を確認する | 二つの入口で同じ処理結果になることの確認 |
| 試すこと自体を楽しめる | 装備が外れ、中からAI本体が現れる演出。演出オフでも同じ操作ができる | 選択した画風、演出のオン／オフ、状態表示の実演 |

最初に押し出すのは「気軽に試せる」「比較して判断できる」「よかった構成を残せる」の三つ。復帰・状態の確認は、その気軽さを支える製品の基礎。ゲーム風の演出は、触ってみたくなる入口と状態理解に使う。

## READMEで見せる最初の一周

1. 今の構成をお気に入りに登録する。
2. 通常・限定解除・零式から別の構成を選ぶ。
3. 選んだモードで新しいタスクを始め、依頼と開始状態を記録する。
4. 成果物、手戻り、所要時間、取得できる使用量と評価メモを振り返る。必要なら後で同じ開始条件から別モードでも試す。
5. 必要な要素を戻す、または手動のみへ変える。
6. 気に入った組み合わせをお気に入りとして残す。以前の構成も呼び戻せる。

画像・デモの主役もこの一周にする。起動画面や解除演出だけでは、比較してお気に入りを残す価値が伝わらないため、公開用のデモは最後のセーブまで含める。

## 説明と検証の約束

- 「合う」は、モデル・環境・依頼・評価の観点に結び付けて説明する。全員に共通の最強構成を前提にしない。
- 外してよくなることも、変わらないことも、悪くなることも比較結果として残す。通常装備を再採用できる体験にする。
- 比較を用意する手間を下げることと、比較結果の因果関係を証明することは区別する。単発の結果から一般的な性能向上を主張しない。
- 同じモデル・推論設定・依頼・開始ファイル・道具・権限を可能な範囲で揃える。メモリや外部サービスなど、共有・変動する条件を記録する。
- 「次回用の設定」と「現在のタスクで確認できた状態」を区別する。新しいタスクでの反映が必要なら明示する。
- ゼロの対象は、選択した管理可能な追加手順・Skill等。仕事の条件と実行権限は保持し、切替用の最小接続口など残る要素も記載する。
- 本体が解き放たれる演出は、ハーネスの着脱を表す。性能の保証や実行権限の解除として宣伝しない。

これらは長い注意書きとして冒頭を埋めるのではなく、各機能の説明と比較・互換性ドキュメントへ配置する。

## 初期版の範囲を守る判断軸

残す核は、保存、3モード、設定・適用状態の表示、条件を揃えた比較、お気に入り、復帰、WebとAIの二つの入口、オフにできる演出。

範囲を絞る際は、対応OS・ツール・バージョンと演出の種類を絞る。構成の世界ランキング、共有マーケット、クラウド同期、自動の最適構成選定は初期の核に含めない。

仮説を観測する最小の場面は、利用者が実際の依頼で別構成を試し、結果を見て採用・維持・復帰のいずれかを選び、その理由と構成を残せること。性能差がなかった場合も、この判断まで辿り着けたかを見る。

利用を広げるための追加案は [feature-candidates.md](feature-candidates.md) に分けた。採用前の仮説であり、既存の初期仕様や実装順を自動的に増やすものではない。

## OSSのDocsを育てる方針

READMEは目指す公開時の価値を基準に育て、現在の実装状況は別の短い欄で明示する。[英語README](../README.md) と [日本語README](../README.ja.md) を用意し、機能と対応範囲の変更を両方へ反映する。

現在は診断CLI、専用検証データと登録した任意ソースの準備・保存・復帰、ローカルGUIがある。日常利用の比較記録、順次再実行、ローカルMCPの接続口も実装した。実行環境全体の検証、デスクトップでのAI操作、製品全体の仕上げは未完成であり、最新の範囲は [status.md](status.md) に記録する。インストールコマンド、対応保証、取得できる指標は、実装と検証ができたものだけを公開手順に記載する。

| 公開へ向けて育てる文書 | 読者が分かること | 内容を確定する材料 |
| --- | --- | --- |
| `README.md` / `README.ja.md` | 誰の何が楽になるか、最初の一周、導入先 | 動く最小体験、短いデモ、現在の対応表 |
| `docs/getting-started.md` | 準備から最初の保存・比較・復帰まで | 新規環境で試した実際の手順 |
| `docs/modes.md` | 3モードで何を外し、何が残るか | 管理対象と対応バージョンごとの意味 |
| `docs/comparing.md` | 条件の揃え方、結果の読み方、メモの残し方 | 開始状態・共有メモリを含む実行例 |
| `docs/favorites.md` | 登録、名前変更、ロード、版、欠落・変更の扱い | セーブ／ロードと衝突の実動作 |
| `docs/ai-commands.md` | 自然言語の依頼例と、操作結果の意味 | 公開するMCPの操作と応答仕様 |
| `docs/compatibility.md` | OS・Codex版・機能別の対応と反映範囲 | 再現可能な検証結果。未対応と未確認も区別 |
| `docs/recovery.md` | 途中失敗、再起動、外部変更からの戻し方 | 中断・競合・接続断を含む復旧テスト |
| `docs/architecture.md` | UI、AIの接続口、共通処理、Codex対応部分の境界 | 実装とデータ形式。構成と演出設定の分離 |
| `CONTRIBUTING.md` | 起動・検証・対応追加・Docs修正の進め方 | 開発手順、必要なチェック、受付窓口 |
| `SECURITY.md` | 設定や秘密情報に関わる問題の非公開報告先 | 利用可能な報告窓口と対象範囲 |
| `LICENSE` と素材・依存物の表記 | コードや同梱素材をどう利用できるか | 利用者のライセンス選択と実際の配布物 |

比較記録の例やIssue用の情報には、構成・バージョン・再現条件を残し、秘密情報や会話履歴を丸ごと要求しない。OSSコードの公開と、お気に入りや個人の設定の公開は別に扱う。

公開前には、英日両方の文書の各機能説明、画面、手順、対応表を実装と証拠に照らして確認する。未実装の文章はロードマップへ移すなど、第三者が現在の機能と誤認しない状態にする。

## 確定した名前と開発順

製品名は **Unharness**。モードの演出上の呼び名は **限定解除 — UNSEAL** と **零式 — TRUEFORM**。

対象OSはmacOSとWindows、対象アプリはCodexデスクトップとClaude Codeデスクトップ。2026-09-08に、まずMac版を完成させる順序へ変更した。MacのCodex版の核、MacのClaude Code対応、CodexによるMac版の統合レビュー・仕上げの順に進める。その後、WindowsでもCodex、Claude Code、統合確認の順で対応する。Claude Codeは自分の連携実装・検証を担当し、Codexが全体の整合性を確認する。

この順序は [delivery.md](delivery.md) に受け渡す成果と受け入れ条件を含めて記載した。専用repoの初期化は完了時点での出発点であり、各組み合わせの対応完了は実機検証に基づいて判断する。
