## 開発用の診断CLI

Node.js 24以上とネイティブのCodex実行ファイルが使える環境で、このrepoから実行します。追加パッケージは不要です。

```text
node bin/unharness.mjs inspect --cwd . --output local-evidence/codex-probe.json
node bin/unharness.mjs inspect-sources --cwd . --output local-evidence/source-inventory.json
node bin/unharness.mjs probe-controls --output local-evidence/source-controls.json
```

全体の `node --test` を実行する前に、`npm ci --ignore-scripts` でロック済み依存関係を導入してください。全体テストにはYAML変換とフロントエンドも含まれます。

`inspect` は別プロセスのCodexから、設定本文などを含まない一覧の要約を取得します。設定変更やデスクトップのモード切替は行いません。[使い方とWindows側への引き継ぎ](docs/codex-probe.md)を参照してください。

`inspect-sources` は、その一覧に標準の指示ファイル候補の確認を加えます。[実設定の読み取り](docs/source-inventory.md)で、取得できた情報と、由来・役割・反映が未確認の範囲を確認できます。個人設定を切替対象に登録する処理ではありません。

`probe-controls` は自分で作った一時的なAGENTS・Skillを6条件で切り替え、Codexが組み立てる入力を確認して後片付けします。個人設定は編集せず、モデルの実行も始めません。確認対象は検証用ソースの挙動であり、デスクトップのモード適用ではありません。[Windowsネイティブでの基準結果](docs/evidence/2026-09-07-windows-baseline.md)には、完了した一覧・専用ソースの確認を記録していますが、デスクトップのモード確認ではありません。[ソース制御の診断](docs/source-controls.md)に詳細があります。

`inspect-desktop --current` は選択中のタスクのローカル記録から、追加ソースや使用量の項目が記録されているかを調べます。本文やトークン合計は出力しません。`desktop-fixture create` は手動で新規タスクを始める検証用フォルダを用意し、専用データだけを復帰できます。WindowsネイティブではGUI経由で条件を満たす新規タスクを観測しましたが、baseline の記録は `not-matched-record` でした。更新通知後の新規タスクで再確認待ちです。モード適用やデスクトップ対応を確認したものではありません。[デスクトップ観測と復帰の手順](docs/desktop-observation.md)と[Windowsの新規タスク証跡](docs/evidence/2026-09-07-windows-fresh-task.md)を参照してください。 Macの専用データでは反映・復帰を観測しましたが、Skill一覧が古い状態を保つ場合がありました。`desktop-fixture refresh` は検証専用ファイルの更新通知を行い、その後のタスクで反映を確かめるためのコマンドです。

`loadouts` で、専用データの登録、版付きのお気に入り保存、変更直前の復旧点、競合を避ける復帰、保存した版とタスク記録の関連付けを扱えます。ローカルGUIも同じ処理を使います。任意の個人設定は別起動の登録ソース画面で扱い、登録済みの対象を扱う[ローカルMCP](docs/ai-commands.md)には通信・共通処理の検証記録と、[範囲を限定した実デスクトップでのAI操作記録](docs/evidence/2026-09-09-ai-desktop-macos.md)があります。[登録・保存・復帰の使い方](docs/loadouts.md)を参照してください。 [Macの実機確認](docs/evidence/2026-09-07-saved-loadout-desktop-macos.md)では、保存した専用データの版と新規タスクの記録を結び付け、通常版への復帰まで確認しました。Windowsの最初の新規タスクは条件を満たしましたが baseline と一致せず、保存版との関連付け成功にはなっていません。

## ローカルGUIで試す

Node.js 24以上で、開発用の画面をビルドして起動します。

```text
npm ci --ignore-scripts
npm run check
npm run build
npm run gui
```

表示されたローカルURLを開きます。保存版の選択・差分確認・適用、現在の設定の保存、新規タスク記録の確認、復旧点への復帰を操作できます。デモを起動するたびに `.unharness/` 内へ新しい専用環境を作り、表示された保存先・scope・再開用の引数で同じ環境を開き直せます。画面には検証専用であることを明示しており、個人のCodex設定は変更しません。完全なモード対応を示すものではありません。[MacでのGUI確認](docs/evidence/2026-09-07-local-gui-macos.md)と、限定的な[Windowsネイティブの確認](docs/evidence/2026-09-07-windows-baseline.md)があります。Windowsの初回GUI確認は以前の演出を対象としており、ブラウザー再起動、演出オフ、狭い表示幅、今回のアニメーションは未確認です。[GUIの使い方と復帰](docs/gui.md)を参照してください。

実際のプロジェクトの設定も読み取り専用で確認する場合は、GUIの再開用引数に `--inspect-cwd <project>` を追加します。新しいデモなら `npm run gui -- --inspect-cwd .` で起動できます。**Codex設定を読み取る**を押すと、追加指示・Skill・hookを中心に一覧を表示します。維持するメモリ・連携・管理ポリシーの情報は折りたたみます。個人設定は変更しません。[設定方法と読み取り範囲](docs/source-inventory.md)を参照してください。

## 登録した任意の設定を準備する

ビルド後に `node bin/unharness.mjs gui --manage-sources --codex-home "<canonical home>" --project "<canonical project>" --codex "<native executable>"` で起動します。候補を確認し、自分が追加した任意の指示・Skillを明示的に選び、通常装備を保存してからUNSEAL／TRUEFORMを選びます。選択は計画のプレビューで、確認後の操作でファイルを準備します。このCodex homeを使う今後のタスクに共通する設定で、元に戻すまで続きます。メモリ、標準の作業継続、権限、プロジェクト要件、hook、未選択のソースは保持します。

[登録ソース画面の使い方](docs/user-source-gui.md)に、起動・再開、保存版、読み戻しとNodeだけでの復旧をまとめています。macOSでのファイル準備とデスクトップの読み込み確認は別で、Windowsの実設定書き込みは制限しています。モデルやデスクトップのタスクは起動しません。

Skill設定の準備では、他の設定とコメントの位置を保持します。Codex側の編集でコメントが失われる場合は、個人ファイルを変更する前に停止します。

[Macの実設定での確認](docs/evidence/2026-09-08-real-source-desktop-macos.md)では、選んだ範囲について3条件と保存したNormalへの復帰を新規タスクで観測しました。画面とCLIには、[選んだタスクを準備済みの版へ関連付ける処理](docs/spec-user-source-observations.md)を追加し、一致・不一致・確認に使えないタスク・不明を日時付きで表示します。準備時点の記録がない旧データは、確認後に設定を準備し直す必要があります。一致が示すのは選択範囲の記録で、デスクトップ全体の対応は引き続き未検証です。

その後にCodex設定が独立して編集され、保持対象の設定だけが変わっている場合、画面は値を出さずに**変更を確認**を表示し、明示操作で現在の設定を新しいNormal版として記録できます。この採用処理は管理対象ファイルを書き換えません。古いお気に入りや復帰点は、現在の共通設定を維持しながら保存済みの選択対象を使うことを明示し、その後に保存した場合だけ新しいお気に入り版になります。[Macの専用環境とビルド済み画面での検査](docs/evidence/2026-09-08-retained-settings-macos.md)では、設定の保持、過去の保存版、中断復旧を確認しました。デスクトップでの読み込みやMac版全体の対応を確認したものではありません。[登録ソース画面の手順](docs/user-source-gui.md)と[保持設定の仕様](docs/spec-retained-settings.md)を参照してください。

同じ画面に**装備**と**比較**のタブがあります。比較では、明示したCodexタスクUUIDの測定と帰属付きの事後評価を、変更できない版として保存します。最大3件を表とゼロ基準のトークン棒で並べ、生の回答は明示操作でプレーンテキストとして開きます。日常利用の記録は、そのタスクでの観測として扱います。オリジナル作成は評価と独立させる方針です。[画面の手順](docs/user-source-gui.md)と[通常利用記録の仕様](docs/spec-comparison-records.md)を参照してください。

タスクの実行前には、折りたたまれた**実行前に条件を保存**から、依頼文・評価基準・打ち切り上限・開始時のファイルを固定できます。未コミットの内容やバイナリも保存し、確認後にファイルが変わると保存を止めます。保存済みの開始条件は変更されません。[Macの専用環境とブラウザーでの検証](docs/evidence/2026-09-08-starting-conditions-macos.md)では、保存・読み戻し・中断・対象変更を確認しました。この[開始条件の保存](docs/spec-starting-conditions.md)ではモデルを起動しません。

保存した条件の**この条件で再実行**から専用の作業場所を1つ準備し、保持設定を確認して、同じ依頼文を新しいローカルタスクへ引き渡せます。コピーやアプリを開く操作でも開始状態を確認し、依頼の送信はユーザーが行います。完了したタスクのUUIDで、記録された依頼・ソース・ルート応答の使用量・別保存の成果物を比較画面へ取り込みます。保存済みの基準で評価し、評価者を明示した訂正と試行時の設定のお気に入り保存もできます。通信が途切れた場合は履歴から保存状態を確認します。[再実行の手順](docs/user-source-gui.md#replay-one-saved-start)と[仕様](docs/spec-sequential-replay.md)を参照してください。性能判定とMac製品全体の検証は引き続き実装・確認します。[登録済み範囲のデスクトップAI操作](docs/evidence/2026-09-09-ai-desktop-macos.md)は一巡を確認しました。

## 「これを外したらどうなる？」を、気軽に試す

AIに仕事をしてもらうために、Skillや指示、作業手順を追加してきた。今度は、そのどれが今のモデルと目の前の仕事に合っているかを確かめたい。

今の構成を保存し、モードを1つ選んで自分の仕事に使う。結果を振り返り、役立つものを戻し、しっくりくる組み合わせをお気に入りに残す。詳しく比べたくなったら、同じ開始条件から別のモードで依頼を再実行できます。比較して今の構成がよいと分かったら、そのまま使い続けられます。

モデルの更新、新しいSkillの追加、プロジェクトの変化、AIの進め方への小さな違和感。どれも、別の構成を試すきっかけになります。

ここでいう**ハーネス**は、Skill、常設の指示、自動処理など、AIの仕事の仕方を形作る周辺の仕組みです。**装備セット**は、それらの組み合わせと、有効・手動のみ・停止の状態を保存したものです。

## 最初の小さなお試し

1. **今の構成を残す。** 「今の設定をお気に入りに登録して」と頼むか、星のボタンで保存します。
2. **別のモードを選ぶ。** 保存したNormal、比較の基準になる零式、そこへ必要な手順を足す限定解除から選びます。目指すモードと現在の実装範囲は下記を参照してください。
3. **新しく試す。** 選んだモードで新しいタスクを始め、依頼と開始条件を記録します。
4. **自分の仕事を振り返る。** 成果物、変更内容、時間、取得できる使用量、自分の評価メモを、保存した結果と一緒に見ます。
5. **合う組み合わせを残す。** 調整した構成をお気に入りに登録して、また使います。以前の装備も呼び戻せます。

得たいのは、自分の仕事に対して理由を持って選べること。指示を減らした結果は、改善、変化なし、大事なものが抜けた、のどれにもなり得ます。

初期の体験は、モードを1つ選んで使う形です。同じ指示を3モードへ自動投入することはなく、条件を揃えた再実行は必要に応じて後から行います。異なる日常業務の記録だけで、モードによる性能改善・悪化を断定しません。

数値比較では、記録されたルート応答のトークンと実行時間を、帰属を明示したチェック・評価・メモと並べます。不明・一部だけの使用量を隠さず、異なる日常業務は中立な観測のまま扱います。性能の解釈には対応する比較条件と明示した判定規則が必要であり、オリジナルの作成条件には使いません。[測定の仕様](docs/comparison-metrics.md)を参照してください。任意の自動評価連携は今後の実装対象です。

## 比較を始める3モード

| モード | 目指す動作 |
| --- | --- |
| 通常装備 | 保存した構成を使います。 |
| 限定解除 — UNSEAL | 零式で残した自動Skillをすべて引き継ぎ、任意の外部Skill・自作Skillを追加できます。追加指示は保存した最小ガイド、またはなしにします。 |
| 零式 — TRUEFORM | 選択した任意の追加指示を外します。自動Skillは、公式マーケットプレイス由来を確認できたプラグインから選んだものだけ残し、その他の制御可能な有効Skillは明示呼び出しのみにします。 |

**表は2026-09-10に合意した目標であり、全体の動作確認は未完了です。** 継承する対象の計算、[新形式の保存・確認付き追加登録・CLI／HTTP／MCPの共通操作・オフラインでの採用取消し](docs/evidence/2026-09-10-mode-inheritance-storage.md)には合成データでの確認があります。[ビルド済み画面](docs/evidence/2026-09-10-mode-inheritance-gui.md)では保存した継承関係を表示し、追加登録後は両モードを別に確認・保存してから準備します。公式プラグインの由来確認と制御、実機での一巡は[残る実装と検証](docs/superpowers/plans/2026-09-10-official-plugin-mode-inheritance.md)が必要です。既存のv1設定とお気に入りは保存時の意味を保ちます。[公式プラグインと継承の仕様](docs/spec-mode-inheritance.md)を参照してください。

**限定解除 = 零式で残したもの + 限定解除だけの追加。** 零式で任意のプラグインを一つも残さない構成も選べます。公式掲載は出どころの条件であって、提供者自身の制作や性能の保証ではありません。私設マーケットの項目は、同じ画面に表示されるだけでは対象になりません。メモリ、作業継続、必須要件、権限、Unharnessの管理・復旧機能は共通保持し、管理機能は公式掲載前でも例外として残します。手動化のためにプラグイン全体や道具との接続を無効にしません。Normalは保存した元の構成で、最も装備が多いことは保証しません。

初期の対象は、任意に追加したグローバルのAGENTS.md／CLAUDE.mdとSkillの自動選択です。標準提供・管理された項目や必須のプロジェクト条件は解除対象にしません。普段はモード選択を中心にし、詳細はAIとの相談で決めます。[モード範囲](docs/harness-scope.md)では現在の目標と過去の条件を区別しています。限定解除で選べる最小ガイドは版付きの比較用文章であり、万能な公式テンプレートではありません。零式の変更は限定解除への影響と一緒に確認して新しい版に保存し、保存だけで設定を適用したり、Normal・過去のお気に入り・比較を書き換えたりしません。

3モードを出発点に、自分で調整した組み合わせもお気に入りとして保存できます。

## 画面でも、AIへの依頼でも

Web画面と自然言語の依頼から、同じローカル処理を呼ぶ体験を目指します。

- 「限定解除に切り替えて」
- 「この依頼を零式でも試して」
- 「今の設定をお気に入りに登録して」
- 「この組み合わせをレビュー用として保存して」
- 「お気に入りのレビュー用に戻して」
- 「今、何が有効？」

お気に入りには、登録した時点の構成を残します。その後に設定を変えても、お気に入りの中身を勝手に変更しません。登録時の名前は省略でき、後から変更できます。

## 装備の変化が見える

ビジュアルは、ドット絵の機械格納庫。外装が開き、内側のAIが見え、零式では本体が姿を現す方向です。AIへの依頼による切替も、Web画面からの操作と同じ状態表示・演出へつながります。

![通常装備、限定解除、零式でAI本体が現れる静止画の構想](docs/assets/04-mecha-release-stages.png)

*当初の静止画によるデザイン案です。現在のGUIは、検証対象を明示した小さな操作フローを実装しています。*

GUIは装備のシーン・演出にPixiJS、操作ボタン・読みやすい状態表示にReactとHTML/CSSを使います。元絵の装甲・支持部・枝状のコアを使い、背景を固定した49コマの動きを描きます。装甲が継ぎ目から開き、支持部が退いてコアが上がり、戻すときも同じコマをたどります。待機中の浮遊や光の動きに加え、演出ONでは最終形態の本体が白青に一層輝きます。再生時の画像生成は不要です。タスク記録やIDなどの技術項目は、折りたたんだ開発用の詳細にまとめています。[描画方針](docs/design.md#selected-rendering-stack)と[同梱素材](docs/gui-artwork.md)を参照してください。外観を選ぶUI全体と、実機でのオリジナル制作手順は引き続き実装・検証しています。

比較で役立つと分かったハーネスは、本体を支える装甲や共鳴する装備としても表現する方針です。未測定時は中立に描き、見た目と測定結果を分けて扱います。

オリジナルは、本体・拘束具・背景のパーツをローカルで再利用します。[ローカルの画面](docs/layered-appearances.md)で選んだPNGを3モードで確認し、作品の保存・旧版への切替・公開項目を指定した画像カードの出力ができます。許可後の公開画面も、対象を限定した画像・作品操作を通じて同じ画面部品を使います。同梱の制作Skillは非公開のローカルMCPで制作場所を用意し、選んだ画像をレビューでき、その私的な場所は公開側へ渡しません。本物の公開サイトからの接続許可と、実機での制作手順の一巡はまだ未検証です。性能による解放条件、3案から一度だけ選ぶ制限、BAD表示への強制は設けず、性能は別に示します。見た目の選択でハーネス設定は変えません。[レイヤー式外観の仕様](docs/personalization.md)を参照してください。

演出はオフにできます。装備の構成は変わらず、状態も文字で確認できます。演出の設定は、お気に入りのハーネス構成とは別に保存します。

## 何を変えたかが分かる

選んだモード、次のタスク向けに用意した設定、実際に確認できた状態を区別して表示します。会話へ読み込み済みの指示は文脈に残るため、比較は新しいタスクから始めます。

比較記録には、装備の版、モデルと推論設定、依頼、開始ファイル、道具、権限、関係するメモリ条件を残す設計です。分離できない条件や取得できない指標は、そのまま明記します。一度の実行は一つの観測として扱います。

復帰では、管理対象の設定を戻し、別途行われた編集を黙って上書きしない設計にします。AIとの接続が失われても、外部の復帰手段を残します。対応する復帰範囲は、検証した手順とともに文書化します。

## 公開状況と参加

Codexの共通処理では、元のNormalと別に、モデル・公式参照を記録したUNSEAL／TRUEFORMの設定案を保存できます。CLI・GUIの操作API・MCPは同じ保存版を使い、採用だけでは設定ファイルや現在のタスクを変更しません。[設定相談の仕様](docs/spec-guided-setup.md)に、検証済みの境界と、未完了の初回導線・実機確認を記録しています。

解除設定の保存後は、ローカル画面やMCPで未登録のSkillを確認・追加できます。従来のNormalと履歴を残し、登録だけでは設定ファイルを変更しません。新規則では追加後の両モードを確認・保存してから、使うモードを別操作で準備します。画面では保存した構成の引き継ぎと追加、設定の確認待ちと準備待ちを区別します。古いお気に入りを戻す際は追加したSkillの扱いも確認できます。[追加登録の流れ](docs/spec-guided-setup.md#additive-skill-enrollment)、[画面の検証記録](docs/evidence/2026-09-10-mode-inheritance-gui.md)。

UnharnessはOSS公開に向けて準備中です。インストール手順と検証済みの対応表はまだありません。両OSを設計対象として保ち、まずMac版を完成させます。

| アプリ | macOS | Windows |
| --- | --- | --- |
| Codexデスクトップ | 初回のMac製品・現在の優先対象 | Mac版完成後の後続 |
| Claude Codeデスクトップ | 既存の連携実装を保持・実機確認は後続 | WindowsのCodex版の後 |

初回のMac版の完成条件はCodex Desktopを対象にします。Claude CodeとWindowsの検証は後続とし、その未完了を初回の完成条件にしません。これは実装対象の表であり、動作確認済みという意味ではありません。[開発順](docs/delivery.md)と[互換性・検証記録](docs/compatibility.md)を参照してください。

初期には、互換性を確かめられる再現情報、小さな比較例、保存・お試し・比較・復帰の流れへのフィードバック、Docsの改善が役立ちます。Unharnessは[MITライセンス](LICENSE)を採用し、同梱する外部コンポーネントのライセンス表示は保持します。公開用の導入手順と報告窓口は準備中です。Webで触れるデモ、手元で使えるプラグイン、実装と検証記録を合わせて公開する計画です。
